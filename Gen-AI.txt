Interviewer: In RAG, your vector search latency spikes from 80 ms to 350 ms during peak traffic. What steps do you take to diagnose and fix it?

Explanation:

When vector search latency suddenly increases from 80 ms to 350 ms during peak load, I follow a structured approach: first diagnose the root cause, then apply quick fixes, and finally implement long-term optimization.


1. Diagnose What’s Causing the Spike

First, I check the system metrics to understand where the slowdown is happening.

Traffic (QPS): Did the number of queries suddenly increase? High QPS can overload vector search nodes.

Latency breakdown (p50, p95, p99): If p99 jumps but p50 is normal, it means only tail queries are slow. (p99 its percentile, shows that 99% of requests are faster)

Resource usage: CPU, RAM, disk I/O, and network bandwidth of the vector database.

Index health: I check if one shard is overloaded, if cache hit rate dropped, or if ANN search parameters (like HNSW efSearch) are too high.

Logs & traces: These help me confirm if the delay comes from the vector search itself or from steps before/after it (embedding, API, re-ranking).


2. Quick Fixes to Reduce Latency Immediately

While diagnosing, I take steps that reduce latency fast:

Add more replicas so traffic gets distributed.

Enable autoscaling during peak traffic windows.

Reduce top-K temporarily to lower the cost per search.

Cache popular queries using Redis or in-memory caching.


3. Find the Root Cause

Once the system stabilizes, I run tests to identify the exact cause:

Replaying peak traffic in staging

Checking if the index parameters are too expensive

Looking for hot shards or uneven data distribution

Testing performance on faster storage (NVMe)


4. Long-Term Optimizations

After identifying the root cause, I apply permanent fixes:

Tune ANN index parameters (efSearch, M, nprobe)

Rebalance shards across nodes

Use memory-optimized or NVMe-backed instances

Add hybrid retrieval (BM25 → Dense) to reduce vector load

Set up better observability and autoscaling

Interviewer: How do you measure hallucination rate, grounding score, and completeness in LLM outputs?

Explanation:

Hallucination Rate, Grounding Score, and Completeness for LLM evaluation.

To measure how reliable the model is.
Here are 3 core metrics we should know:

1. Hallucination Rate:

Measures how often the LLM generates false or unsupported claims.

If an answer is not found in context or contradicts facts → it’s a hallucination.

How it’s measured:

Compare model output with ground-truth documents

Use NLI models (Natural Language Inference models)→ check answer alignment with key information.


SMEs label incorrect sentences

Formula:
Hallucination Rate = Hallucinated Statements / Total Statements

Lower = Better



2. Grounding Score:

Measures how well the response is supported by retrieved documents.
(Critical in RAG systems.)

How it’s measured:

Check if each answer sentence is entailed by context

Use semantic similarity or RAGAS Groundedness

Higher similarity → better grounding

Scale:
0 = Not grounded
1 = Fully grounded

Higher = Better



3. Completeness Score:

Checks whether the output covers all required parts of the question.

How it’s measured:

Extract key answer elements (facts, steps, fields)

Verify if each is present in the output

Use recall-based metrics or evaluator LLMs

Formula:
Completeness = Covered Elements / Expected Elements

Higher = Better


▪︎ These Metrics Matter Because an LLM can: hallucinate facts, skip important details, ignore the source data.

🚀KV Caching in LLMs

Large Language Models (LLMs) like GPT, LLaMA, Mistral, and others rely on the Transformer architecture.

But one of the biggest challenges in transformers is speed, especially during text generation.

And that's where KV Caching comes into the picture.

It is one of the most popular technique that makes inference much faster, cheaper, and more scalable.

What is KV Caching?
In a Transformer decoder, each new token attends to all previous tokens.
At every generation step, the model internally computes:
K → Keys
V → Values
Q → Query

But there's a catch...
It's observed that as a new token is generated, the Keys and Values used for previous tokens do not change.

So, we can calculate the KV vectors for just once and only compute the Query vector for the new tokens.

How KV Caching Works?

👉Without KV Cache
At token t=100 → you compute attention over 1…100
At token t=101 → recompute 1…101
At token t=102 → recompute 1…102

Total complexity: 𝗢(𝗻²)

👉With KV Cache
At token t=100 → you compute attention over stored K/V
At token t=101 → reuse K/V + compute only for token 101
At token t=102 → reuse K/V + compute only for token 102

Total complexity: 𝗢(𝗻)
